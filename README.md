# Контроль расширения прав ИИ-плагинов

**Учебный MVP команды 33 · тема KIB-34**

Одностраничное веб-приложение, которое сравнивает два учебных JSON-манифеста ИИ-плагина, показывает добавленные разрешения, передаёт расширение доступа на согласование и записывает действия в журнал текущей вкладки.

> Это демонстрационный макет, а не средство защиты корпоративной инфраструктуры. Приложение не устанавливает плагины, не выдаёт реальные права, не проверяет код и подлинность манифестов и не заменяет аутентификацию.

## 2. Проблема и целевой пользователь

Сотрудники небольших компаний устанавливают сторонние программы и ИИ-помощников. При обновлении плагин может запросить новые права: читать рабочие файлы, изменять документы или отправлять письма от имени сотрудника. Уже разрешённый ранее плагин не вызывает прежнего настороженного отношения, а сотрудник может не заметить расширение доступа и не понять его последствия.

**Целевые пользователи учебного сценария:**

- сотрудник малой компании, который подключает и обновляет цифровые инструменты;
- ответственный согласующий, который проверяет дополнительный доступ перед демонстрационным «продолжением».

**Проверяемая проблема:** расширение заявленных прав не должно автоматически считаться допустимым только потому, что плагин был разрешён раньше. Решение должно относиться к конкретной паре версий и полному составу прав.

## 3. Что делает MVP

1. Принимает два JSON-файла: текущую и новую версию манифеста.
2. Проверяет синтаксис, обязательные поля, типы, пустые значения и совпадение `plugin_id`.
3. Вычисляет новые права как разность множеств: `permissions(новая версия) − permissions(текущая версия)`.
4. Показывает для каждого нового права понятное учебное объяснение либо честное предупреждение о неизвестном праве.
5. Позволяет сотруднику ввести обоснование и передать запрос согласующему.
6. Позволяет демонстрационному согласующему согласовать или отклонить именно текущий запрос.
7. Записывает передачу и решение в журнал текущей вкладки с версиями, правами, ролью, комментарием и фактическим временем.

Приложение не содержит серверной части, базы данных, регистрации, навигации между страницами, реальной модели ИИ и подключения к корпоративным сервисам. Все данные обрабатываются локально в браузере.

## 6. Демонстрационные данные

### Основной набор A — `team-assistant`

`manifest_old.json`:

```json
{
  "plugin_id": "team-assistant",
  "version": "1.0",
  "permissions": ["profile.read"]
}
```

`manifest_new.json`:

```json
{
  "plugin_id": "team-assistant",
  "version": "1.1",
  "permissions": [
    "profile.read",
    "drive.files.read",
    "mail.send"
  ]
}
```

Ожидаемый результат: ровно `drive.files.read` и `mail.send`. `profile.read` не является новым правом.

### Дополнительный набор B — `office-helper`

Файлы находятся в `denis_cybersecurity/manifests/`:

- `01_current_v1.0.0.json` — `documents.read`;
- `02_update_v1.1.0_add_write.json` — `documents.read`, `documents.write`.

Ожидаемое новое право: `documents.write`. Приложение обрабатывает этот набор тем же алгоритмом, без отдельного режима.

### Кнопка «Заполнить учебным примером»

Подставляет пару `team-assistant` из раздела 6 и сразу выполняет сравнение. Это позволяет пройти весь сценарий без выбора файлов. Ручная загрузка через стандартные поля File API также поддерживается.

### Воспроизведение трёх состояний

1. **Состояние 1.** Открыть страницу → «Заполнить учебным примером». Появятся `manifest_old.json · версия 1.0`, `manifest_new.json · версия 1.1`, два новых права, жёлтый статус «Нужно согласование…», пустой журнал.
2. **Состояние 2.** В поле комментария ввести «Нужна проверка: отправка писем не требуется для поиска файлов» → «Передать на согласование». Статус сменится на ожидание, появится одна запись, сотрудник не сможет нажать согласование или отказ.
3. **Состояние 3.** Выбрать роль «Согласующий · демо» → заменить комментарий на «Отклонено: для поиска файлов не требуется отправка писем» → «Отклонить новые права». Появятся статус отказа и вторая запись журнала.

Альтернативная ветка: после состояния 2 нажать «Согласовать новые права». Появятся статус согласования и две записи. Для чистого повторного прохождения нажать «Сбросить макет».

## 7. Формат манифеста и проверка

Обязательны три поля:

| Поле | Правило |
|---|---|
| `plugin_id` | непустая строка без пробелов в начале и конце; должна совпадать в обоих файлах |
| `version` | непустая строка без пробелов в начале и конце; не число; порядок версий не вычисляется |
| `permissions` | массив непустых строк без пробелов в начале и конце; `[]` допустим |

Дополнительно:

- корень JSON обязан быть объектом, а не массивом, строкой или `null`;
- отсутствие `permissions` — ошибка, а не пустой список;
- числа и другие типы не преобразуются в строки;
- дополнительные поля допускаются, но не участвуют в сравнении;
- размер каждого файла ограничен 1 МБ;
- версии в загруженной паре должны различаться (требование командного сценария);
- записи `permissions` сравниваются с учётом регистра и точного написания;
- порядок элементов и повторы не влияют на результат.

Сообщение об ошибке содержит:

1. имя файла;
2. поле;
3. объяснение проблемы;
4. действие для исправления.

Технический stack trace не выводится. После ошибки чтения или проверки текущий допуск сбрасывается; положительная запись в журнал не создаётся.

**Ограничение:** `JSON.parse` не обнаруживает дубли ключей внутри объекта. Такие случаи не входят в учебный набор, и приложение не заявляет их поддержку. Промышленной реализации нужен строгий парсер.

## 8. Алгоритм сравнения

```text
oldSet = уникальные строки permissions текущей версии
newSet = уникальные строки permissions новой версии
newRights = элементы newSet, которых нет в oldSet
```

Свойства алгоритма:

- порядок не важен;
- повторяющиеся значения не создают новых прав;
- удаление не считается добавлением;
- замена при том же количестве элементов обнаруживается;
- изменение только `version` не создаёт новых прав;
- пустая текущая база не отключает проверку;
- неизвестная строка всё равно сравнивается и показывается.

Удалённые права при необходимости выводятся отдельной серой строкой под списком новых прав и не смешиваются с добавленными.

## 9. Словарь учебных разрешений

| Разрешение | Объяснение в интерфейсе |
|---|---|
| `profile.read` | чтение базовых данных профиля |
| `drive.files.read` | чтение рабочих файлов |
| `mail.send` | отправка писем с подключённого адреса |
| `documents.read` | чтение документов |
| `documents.write` | создание и изменение документов; чтение этим правом отдельно не разрешается |
| `documents.export` | формирование выгрузки или копии документов; само по себе не доказывает отправку третьему лицу |
| `calendar.share` | назначение неизвестно; интерфейс не придумывает смысл и требует уточнения у владельца плагина |

Все строки — условные учебные обозначения. Они не являются официальным перечнем разрешений Google, OpenAI, ENISA, Slack, GitHub или иной платформы.

Для неизвестного разрешения показывается точный идентификатор, пометка «нет описания» и текст:

> Назначение права неизвестно. Уточните доступные данные и действия у владельца плагина перед согласованием.

## 10. Процесс согласования

### Роли

Переключатель содержит:

- «Сотрудник» — выбран по умолчанию;
- «Согласующий · демо».

Это **не аутентификация** и не разграничение доступа. Переключатель нужен только для демонстрации последовательности «сотрудник → согласующий».

### Сценарий

1. После сравнения с новыми правами появляется статус «Нужно согласование…».
2. Сотрудник вводит непустой комментарий. Только после этого активируется «Передать на согласование».
3. После передачи статус меняется на «Ожидает согласования…», создаётся первая запись журнала. Повторная передача того же запроса недоступна. Сотрудник не может нажать «Согласовать» или «Отклонить».
4. Пользователь явно переключает демонстрационную роль на согласующего. Для решения нужен непустой комментарий.
5. Согласующий нажимает «Согласовать новые права» или «Отклонить новые права». Создаётся вторая запись журнала. Повторное решение недоступно.
6. Статус показывает результат. Никакое реальное обновление при этом не выполняется.

### Привязка решения к запросу

Решение относится не только к номеру версии, а к нормализованному снимку:

```text
plugin_id
+ версия текущего манифеста
+ версия нового манифеста
+ полный набор старых прав (без повторов, отсортирован)
+ полный набор новых прав (без повторов, отсортирован)
```

Из этого строится `requestKey`. Текущее состояние передаётся и решения проверяет, что ключ совпадает.

Текущий допуск и комментарий сбрасываются:

- при выборе нового файла с любой стороны;
- при изменении содержимого кандидата при том же номере версии;
- при замене текущей базы;
- при ошибке чтения или проверки следующего файла.

Повторное нажатие «Сравнить права» без изменения входов не открывает повторную передачу или повторное решение: согласование остаётся связанным с тем же запросом. Чтобы начать новую проверку, нужно изменить файл или сбросить макет.

Старые записи остаются в журнале как история, но не дают согласия новому запросу.

Согласование не заменяет текущий JSON новой версией и не считается установкой обновления.

## 11. Журнал

Журнал хранится только в памяти текущей вкладки и исчезает после перезагрузки — так требует исходный макет. `localStorage` и постоянный аудит в обязательную реализацию не добавлены.

Пять видимых колонок:

1. Время;
2. Версии;
3. Роль;
4. Событие;
5. Новые права.

В записи сохраняются:

- `plugin_id`;
- старая и новая версии;
- полные снимки старого и нового наборов прав;
- новые права;
- действие;
- демонстрационная роль;
- комментарий;
- фактическое время с датой, секундами и смещением часового пояса;
- ключ запроса.

Комментарий и `plugin_id` отображаются дополнительными строками внутри записи. Записи не переименовываются при следующем сравнении.

## 13. Модель угроз и ограничения

### Что моделирует MVP

- риск незамеченного расширения заявленных прав при обновлении;
- необходимость отдельного решения для конкретной пары версий и состава прав;
- сброс прежнего допуска при изменении входных данных или ошибке;
- понятное отображение неизвестного права;
- базовую прослеживаемость решения в журнале текущей вкладки.

### Что остаётся вне защиты

Приложение:

- **не проверяет реальное поведение кода плагина**;
- **не анализирует вредоносный код**;
- **не проверяет подлинность или подпись манифестов**;
- **не проверяет, что текущий манифест соответствует реально установленной версии**;
- **не выдаёт реальные разрешения** и не отзывает их;
- **не блокирует установку обновлений** во внешнем сервисе;
- **не имеет настоящей аутентификации и разграничения ролей**;
- **не обеспечивает защищённый и неизменяемый журнал**;
- **не обнаруживает скрытое расширение смысла уже существующего разрешения**, действия с ранее выданными правами и вредоносное поведение без новых строк;
- **не доказывает безопасность обновления** при отсутствии новых строк.

Дополнительные ограничения:

- дубли ключей JSON не обнаруживаются;
- существенные изменения в дополнительных полях игнорируются;
- журнал хранится в памяти и может быть изменён через инструменты браузера;
- решение опирается на нормализованный снимок, а не на криптографическую подпись;
- нет интеграции с OAuth/OIDC, IAM, каталогом приложений или системой установки плагинов;
- нет защиты от подмены самого веб-приложения на локальном компьютере.

### Допущения учебного сценария

- текущий манифест выбран правильно и соответствует разрешённой базе;
- оба файла правдиво перечисляют запрашиваемые права;
- решение принимает уполномоченный человек;
- браузер и локальное окружение работают корректно.

Эти допущения не проверяются механизмом сравнения.

## 14. Безопасность реализации

- всё содержимое JSON остаётся в браузере; приложение не отправляет его на сторонние серверы;
- нет `fetch`, `XMLHttpRequest`, внешних API, аналитики и корпоративных подключений;
- динамические значения (имена файлов, права, комментарии) вставляются через `textContent`, без `innerHTML`;
- размер файла проверяется до чтения;
- ошибки не содержат технического stack trace;
- запоздавшие результаты чтения файла отбрасываются по токену актуальной стороны и не могут подменить новую пару;
- при наличии любой активной ошибки передача и решение заблокированы, даже если в состоянии остался прежний запрос;
- перед сравнением сбрасывается прежний допуск;
- журнал не создаёт запись при загрузке, сравнении, ошибке или отсутствии новых прав;
- никаких реальных разрешений не выдаётся.

## 15. Использованные ИИ-инструменты

- **OpenCode** с моделью **DeepSeek V4.1 Flash 1017** — реализация HTML/CSS/JavaScript, автоматические тесты, браузерный прогон, подготовка README, `TEST_RESULTS.md` и `PROMPT_LOG.md`.
- **Chrome DevTools Protocol** и headless Google Chrome — фактическая проверка кнопок, загрузки файлов, состояния интерфейса и адаптивности.
- **ChatGPT** — по раскрытию Дениса, использовался для подготовки его учебных манифестов, черновика модели угроз и тестовых сценариев. Эти материалы не выдаются за независимую проверку Дениса или команды.

Аналитические выводы в `threat_model_and_tests.docx` самим документом помечены как черновые выводы ИИ и требуют самостоятельной проверки. Текст README, `TEST_RESULTS.md` и `PROMPT_LOG.md` также подготовлен ИИ-агентом по фактическим материалам и результатам; авторская проверка и итоговые формулировки остаются за участниками команды в соответствии с требованием методички.

Отличие учебного MVP — единый демонстрационный сценарий: сравнение двух JSON → показ новых прав → понятное объяснение → отдельная передача запроса → решение согласующего → журнал. Ценность макета в цельности сценария для обучения, а не в новизне отдельного механизма.

## 17. Сценарий защиты на 4 минуты

| Время | Что показать |

Резервная демонстрация: «Сбросить макет» → загрузить `manifest_old.json` и `manifest_new.json` через файловые поля → «Сравнить права» → одобрить во второй ветке. Пользовательские тесты и видео не выдумывались и не записывались.

## 18. Расхождения требований

Подробно — в `TEST_RESULTS.md`, раздел «Расхождения требований». Кратко:

1. **Один шаг у Дениса vs два шага в командном макете.** В T03/T04 Денис описывает прямое нажатие «Согласовать/Отклонить». Командный макет требует: сотрудник передаёт заявку → согласующий решает. Реализован командный сценарий; T03/T04 адаптированы, проверяемое свойство сохранено.
2. **Формулировки статусов.** До передачи заявки командный макет использует «Нужно согласование…», а не «Ожидает согласования». Слово «ожидает» зарезервировано для состояния после передачи. Это сохраняет различие между обнаружением прав и поданной заявкой.
3. **Количество записей журнала.** Из-за двухшагового процесса после отказа/согласования появляются две записи (передача и решение), а не одна.
4. **Версии.** Контракт Дениса не требует обязательного различия версий и запрещает автоматически выводить их порядок. Требование командного задания дополнительно требует, чтобы версии в паре различались. Порядок по-прежнему не вычисляется; равенство версий отклоняется.
5. **Удалённые права.** Денис не требует их показа; в MVP они выводятся отдельной строкой, чтобы удаление не путалось с добавлением.
6. **Роль и аутентификация.** В материалах Дениса решение иногда описывается как действие сотрудника. В командном макете есть демонстрационный согласующий. Переключатель роли не является авторизацией.
7. **Статусы T05/T18.** Денис пишет «Ожидает согласования» сразу после замены файла; в командном интерфейсе после замены нужно снова нажать «Сравнить права», после чего отображается «Нужно согласование…». Проверяемое свойство — отсутствие переноса согласия — выполнено.

## 19. План развития

- независимый прогон `test_protocol.xlsx` Денисом и заполнение фактических результатов;
- пользовательский тест с целевым сотрудником без подсказок;
- подпись манифестов и получение текущей версии из доверенного источника;
- строгий JSON-парсер с обнаружением дублей ключей;
- реальная аутентификация и разграничение ролей;
- интеграция решения с фактической выдачей/отзывом прав;
- защищённый append-only журнал на сервере;
- политика повторного согласования при изменении смысла существующего права;
- проверка доступности с клавиатуры и скринридером, аудит контраста;
- тесты Safari/Firefox и на физических мобильных устройствах;
- нагрузочные и конкурентные сценарии.
