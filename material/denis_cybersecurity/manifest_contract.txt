ПРЕДЛАГАЕМЫЙ КОНТРАКТ МАНИФЕСТОВ И ПРОЦЕССА СОГЛАСОВАНИЯ
Для Георгия и Дениса. Подготовлено 24 ноября 2026 года.
Статус: техническое предложение, ещё не согласовано с разработчиком.

1. ЧТО СРАВНИВАЕМ
Два JSON-файла одного вымышленного плагина: текущий разрешённый набор и кандидат на обновление. Реальное подключение плагина не выполняется.
Текущий файл — заданная пользователем база. Прототип не доказывает её подлинность и соответствие реально установленной версии.

2. ОБЯЗАТЕЛЬНЫЕ ПОЛЯ
plugin_id — строковый идентификатор плагина. В обоих файлах должен точно совпадать.
version — строковое обозначение версии. Не число. В этой учебной модели порядок версий автоматически не проверяется.
permissions — массив строк с разрешениями; пустой массив [] допустим.
Идентификатор, версия и каждое право должны быть непустыми строками без пробелов по краям. Нельзя автоматически превращать число в строку или отсутствие permissions в [].
Корневое значение JSON должно быть объектом, не массивом и не null.
Дополнительные поля допустимы, но эта модель их не использует. Существенные изменения, спрятанные в дополнительных полях, находятся вне охвата.
Порядок прав и повторения игнорируются при сравнении. Регистр и написание значимы: автоматически исправлять неизвестные разрешения нельзя.
Дубли ключей внутри JSON не входят в подготовленные сценарии; для промышленной реализации нужен строгий парсер, исключающий неоднозначное чтение.

Пример текущей версии:
{
  "plugin_id": "office-helper",
  "version": "1.0.0",
  "permissions": ["documents.read"]
}

Пример обновления:
{
  "plugin_id": "office-helper",
  "version": "1.1.0",
  "permissions": ["documents.read", "documents.write"]
}

3. СМЫСЛ УЧЕБНЫХ ПРАВ
documents.read — читать документы в заданной учебной области доступа.
documents.write — создавать или изменять документы в этой области. В учебном сравнении не включает автоматически documents.read или удаление.
documents.export — формировать выгрузку/копию документов. Само по себе не доказывает передачу данных внешнему адресату.
calendar.share — намеренно неизвестное словарю интерфейса право. Его точное имя нужно показать; смысл не угадывать, решение всё равно требуется.
Эти строки придуманы для проекта. Они не заявлены как стандарт ENISA, OpenAI, Slack, GitHub или иной платформы.

4. АЛГОРИТМ
Сначала проверить оба файла, обязательные поля и совпадение plugin_id.
Текущие права = множество строк старого permissions.
Права кандидата = множество строк нового permissions.
Новые права = права кандидата минус текущие права.
Сравнивать именно состав, а не количество элементов или буквальный порядок JSON.
При необходимости отсортировать вывод для читаемости; сортировка не меняет смысл.

5. СОСТОЯНИЯ
Ожидание файлов — не хватает входных данных; решение и допуск отсутствуют.
Ошибка — файл не читается, не соответствует формату или относится к другому плагину; решение и допуск отсутствуют.
Новые права отсутствуют — отдельно согласовывать расширение доступа не требуется. Это не означает «код безопасен» или «сотрудник согласовал».
Ожидает согласования — новые права есть; текущий запрос не разрешён.
Согласовано — сотрудник явно согласовал конкретный запрос; решение записано в журнале, разрешено продолжение учебного процесса для этого запроса.
Отклонено — сотрудник отказал; для этого запроса допуска нет, отказ отражён в журнале.
Под «блокировкой» в MVP понимается отсутствие статуса допуска. Если есть отдельная кнопка продолжения демонстрационного обновления, она должна быть недоступна до согласования. Цвет или надпись не должны расходиться с фактическим состоянием процесса.
Прототип не обязан устанавливать настоящий плагин или создавать интеграцию для обновления.

6. К ЧЕМУ ОТНОСИТСЯ СОГЛАСИЕ
Решение относится к plugin_id, старой и новой версиям, а также к полным нормализованным наборам прав обеих сторон.
При изменении входной пары прежний текущий допуск сбрасывается; сначала заново проверяются входные данные и вычисляются новые права.
Номер версии не единственное основание доверия: если содержимое кандидата изменилось при том же version, требуется новое решение для нового состава прав.
Для MVP достаточно хранить эти значения/снимок запроса и сравнивать их. Хеширование не является обязательным требованием.
История решений сохраняется как история, но автоматически не разрешает изменённый запрос.
Повторное использование решения после повторной загрузки полностью той же пары и восстановление состояния после перезагрузки пока не требуются; их поведение следует описать после получения сборки.

Пример A — отдельное согласование обязательно:
Текущий 1.0.0: [documents.read]. Согласовали кандидата 1.1.0: [documents.read, documents.write].
Текущий файл не меняем. Загружаем кандидата 1.2.0: [documents.read, documents.write].
Относительно 1.0.0 право documents.write всё ещё новое, а решение было для 1.1.0. Статус снова «Ожидает согласования».

Пример B — расширения уже нет:
Текущий файл явно загружен как 1.1.0: [documents.read, documents.write].
Кандидат 1.2.0: [documents.read, documents.write]. Новых прав нет.
Нажатие «Согласовать» само по себе не подменяет текущий файл и не подтверждает факт установки.

7. ЖУРНАЛ
Для каждого явного согласования/отказа: plugin_id, старая версия, новая версия, новые права, решение, время решения с часовым поясом.
Желательно хранить также снимки полных наборов прав и учебную роль согласующего — это объясняет, к какому запросу относилось решение. Это рекомендация для развития, а не требование добавлять регистрацию пользователей.
Запись не должна появляться как «Согласовано» при ошибке, ожидании файлов, отсутствии новых прав или простой загрузке файла.
Время фиксируется при решении, а не берётся из учебного JSON. В тестах не подставлять вымышленное фактическое время.
После выбора другого кандидата старые записи не переименовываются под него.

8. ОШИБКИ
Ошибка сообщает, что неверно и в каком файле: синтаксис JSON, отсутствующее поле, неверный тип, пустая строка, разные плагины.
Технический стек вызовов сотруднику не нужен. Нельзя сохранять прежний допуск после новой ошибки.
Одинаковые проверки формата применяются к обоим входам.

9. ОГРАНИЧЕНИЯ
Манифест — заявление о правах; он не доказывает действительное поведение кода.
Нет проверки подписи, источника поставки, настоящих OAuth/MCP-разрешений, аутентификации согласующего, неподделываемости журнала и блокировки обновлений внешнего сервиса.
Изменение значения уже существующего права, скрытый доступ и вредоносный код без новых заявленных прав этим методом не обнаруживаются.
Крупные файлы, нагрузка, одновременные решения и долговременная сохранность журнала — отдельный будущий этап.
